# LUMEN — E2E reservation, inbox, Chrome push

## What an end user means by an incoming request and a popup

A hold is an authoritative LUMEN reservation with status ready or queued. Both states must be visible to librarians in **Banco → Circolazione**. Only a ready reservation offers the physical checkout action. New holds produce staff inbox events transactionally.

An in-app message has three *different* delivery surfaces:

1. Persistent inbox (source of truth): every intended active recipient sees the message in Comunicazioni.
2. Foreground browser tab: compact unread count and best-effort new-message toast based on authenticated inbox polling.
3. Chrome/OS system notification: requires HTTPS/secure origin, VAPID, compatible Push/Notification APIs, explicit browser permission, a device subscription and OS delivery. Not guaranteed; push provider acceptance is not proof of OS display.

## Codespaces commands

Normal fully usable app: `npm run dev` → forwarded private port 3000.
Optional push-equipped demo: `npm run dev:push` → same app, stable locally generated VAPID secrets in ignored data/dev-push-vapid.json (permissions 0600). Open HTTPS forwarded URL (or secure localhost), sign in, Settings → Activate notifications on this device. In another browser profile sign in as librarian and send a staff broadcast. Observe recipient inbox even if OS push is blocked.

Demo identities: student@lumen.local, faculty@lumen.local, librarian@lumen.local; password Demo1234! (development only).

## Render setup

Production Render remains `npm start` via render.yaml and mandatory prestart. For OS push supply Render environment secrets VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY, VAPID_SUBJECT (mailto:address-of-library); use a distinct production pair securely generated by `npx web-push generate-vapid-keys`, not the development pair. HTTPS, user opt-in and physical Chrome/Windows/Android tests are mandatory. Browser subscription keys and sender identity are origin scoped. Never commit the private key.

## DoD by level

| Level | Testable obligation | Evidence |
|---|---|---|
| Local | ready/queued hold writes, staff fan-out, FIFO, retries do not duplicate events | domain mutation tests |
| Local | status-based checkout CTA, no queue promotion by UI | staff render/HTTP |
| Local | staff-only paged GET /api/staff/holds (bounded limit and offset) | HTTP 401/403/400 + 200 |
| Intermediate | student or faculty hold → librarian desk + inbox; faculty acquisition → librarian Acquisition + inbox | service + Chromium |
| Intermediate | broadcast → recipient-specific inbox and honest result count; no made-up OS delivery | HTTP + Chromium |
| Intermediate | foreground unread counter/toast observes only new authenticated messages, resets on identity switch | watcher unit tests |
| Global | fresh Codespaces npm run dev, opt-in npm run dev:push, Render npm start, Node+browser CI | commit-specific GitHub Actions |
| External | real Chrome OS notification in background after permission, delivery click and opt-out; Render live restart and offsite restore | BLOCKED until external test |
| Enterprise | live Koha/IdP, 2,000 mixed concurrency, HA/DR, security and accessibility reviews | BLOCKED |

## Negative mutations / falsifiers

An inactive librarian receiving notices; patron reading staff queue; queued hold showing checkout; idempotent replay producing another notice; staff broadcast changing recipients; VAPID-off reporting OS delivery; cross-user push enrollment; a stale notification shown as a new user login alert; any OS payload containing book/person data: each is a release blocker.
